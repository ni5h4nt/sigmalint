## Phase 3: PR-A.3 fix list-of-dict walker gap in `src/sigmalint/rules/fp_risk.py` [depends: 1, 2] [est: ~50 lines]

**Files:**
- Modify: `src/sigmalint/rules/fp_risk.py` — replace `_selectors()` with `_selectors_iter()`; update FP001 + FP002 call sites accordingly

**Current implementation** (`src/sigmalint/rules/fp_risk.py:21-22`):

```python
def _selectors(detection: dict) -> dict[str, dict]:
    return {k: v for k, v in detection.items() if k != "condition" and isinstance(v, dict)}
```

This silently drops list-of-dict selectors — the same pattern that bit TAX walker in v0.1.2. FP001 and FP002 both use `_selectors()` so both inherit the gap.

**Why a merging fix is wrong.** The intuitive "flatten the list into one dict with `update()`" approach has two failure modes:

1. **For FP002**: `[{Field: 'a*'}, {Field: 'b*'}]` would merge into `{Field: 'b*'}` — the first dict's wildcard is silently overwritten, so FP002 misses one of two distinct wildcard findings.
2. **For FP001**: merging a 2-item list-of-dict into one dict produces a 2-field dict, which makes FP001 think the selector is multi-field broad rather than a multi-branch OR.

**Fix:** return an iterable of `(selector_name, body_dict)` tuples. A dict selector yields one tuple; a list-of-dict yields *N* tuples sharing the same name. Each rule chooses how to interpret the OR-shape.

```python
def _selectors_iter(detection: dict) -> Iterable[tuple[str, dict]]:
    """Yield (selector_name, body) for every dict-shaped detection branch.

    A `dict` selector yields one (name, body). A `list-of-dict` selector
    yields one (name, body) per dict member - same selector name, multiple
    bodies. Rules that need to distinguish "one selector" from "one branch"
    must inspect both the distinct-name set and the tuple count.
    """
    for k, v in detection.items():
        if k == "condition":
            continue
        if isinstance(v, dict):
            yield k, v
        elif isinstance(v, list):
            for item in v:
                if isinstance(item, dict):
                    yield k, item
```

**FP001 call-site update** — uses both distinct-name count AND tuple count to identify "single broad":

```python
def check(self, parsed, ctx):
    detection = parsed.data.get("detection") or {}
    sels = list(_selectors_iter(detection))
    distinct_names = {n for n, _ in sels}
    if len(distinct_names) != 1:
        return
    name = next(iter(distinct_names))
    if _is_filter_selector(name):
        return
    # list-of-dict with >1 entry is a multi-branch OR, not "single broad"
    if len(sels) != 1:
        return
    (_, body) = sels[0]
    # ... existing field-count + short-scalar check
```

**FP002 call-site update** — iterates per-tuple; duplicate findings across OR-branches are correct:

```python
def check(self, parsed, ctx):
    for selname, body in _selectors_iter(parsed.data.get("detection") or {}):
        for field, value in body.items():
            # ... existing wildcard check; emit one finding per (branch, field) wildcard
```

This preserves correct semantics on both shapes:

| Input | FP001 fires? | FP002 fires? |
|---|---|---|
| `{F: 'abc'}` (dict, 1 field, len-3 scalar) | Yes (1) — meets `len < 6` | No (no wildcard) |
| `{F: '*foobar*'}` (dict, len-8 wildcard) | No — `len('*foobar*') == 8`, not `< 6` | Yes (1, `\|contains`) |
| `{F: '*a*'}` (dict, len-3 wildcard) | Yes (1) — short scalar fires FP001 too | Yes (1, `\|contains`) — both rules fire on the same field |
| `[{F: 'abc'}]` (list-of-dict, 1 item, 1 field, short scalar) | Yes (1) | No |
| `[{F: '*a*'}, {F: '*b*'}]` (list-of-dict, 2 wildcards same field) | No (multi-branch — not "single") | Yes (2) — both branches |
| `[{F: 'abc'}, {G: 'xyz'}]` (list-of-dict, 2 different fields) | No (multi-branch) | No (no wildcards) |

## Phase 5: PR-B.1 FP003 contrived shape coverage + harness extension [depends: 4] [est: ~250 lines]

**Files:**
- Create: `tests/contrived/FP003/{manifest.yml, pos_*.yml, neg_*.yml, edge_*.yml}` (estimated ~12 fixtures)
- Modify: `tests/contrived/test_contrived.py` — add `_RULE_MAP["FP003"]` entry **and** extend the harness to honor a `filters:` field in manifest cases

**Rule under test:** FP003 fires for rules in noisy logsource categories (`process_creation`, `registry_event`, `file_event`, `network_connection`) whose condition AST has no negated selector AND no external Sigma Filter file applies.

**Harness extension** — the current `_ctx()` builds a `RunContext` with only taxonomy/modifiers/config; no per-case filters. To exercise FP003's external-Sigma-Filter path, the manifest schema gains an optional per-case `filters:` field whose value is a list of filter specs that map directly to the existing `SigmaFilter` dataclass.

**Concrete API** — `sigmalint.core.filters.SigmaFilter` is already a frozen dataclass with four fields (verified from `src/sigmalint/core/filters.py:32-45`):

```python
@dataclass(frozen=True, slots=True)
class SigmaFilter:
    path: str
    targets_ids: tuple[str, ...]
    targets_names: tuple[str, ...]
    condition: str
```

So the harness can construct filters in-process from manifest data without writing filter YAML files or invoking `discover_filters(...)`:

```yaml
# manifest example
negatives:
  - file: neg_external_filter_negates.yml
    expect: 0
    filters:
      - targets_ids: ["6ba9c5b1-8f7e-4d2a-b5e1-1234567890ab"]   # id of the fixture
        targets_names: []
        # The selector name must match _is_filter_selector(): `filter`,
        # `filter_*`, or `_*`. Anything else would not be treated as a
        # filter-class selector even when negated.
        condition: "not filter_external"
```

Harness diff (concrete):

```python
from sigmalint.core.filters import SigmaFilter

def _build_filters(specs: list[dict] | None) -> list[SigmaFilter]:
    return [
        SigmaFilter(
            path="<contrived>",
            targets_ids=tuple(spec.get("targets_ids") or ()),
            targets_names=tuple(spec.get("targets_names") or ()),
            condition=spec["condition"],
        )
        for spec in (specs or [])
    ]

def _ctx(tmp_path: Path, filter_specs: list[dict] | None = None) -> RunContext:
    return RunContext(
        taxonomy=SigmaTaxonomy(tmp_path),
        modifiers=SigmaModifiers(tmp_path),
        config=Config(),
        filters=_build_filters(filter_specs),
    )
```

The parametrized test reads `case.get("filters")` and passes it to `_ctx()`. Cases without `filters:` get an empty filter list, identical to current behaviour — no risk of breaking existing dimensions.

**Fallback if `RunContext` doesn't accept a `filters=` kwarg**: check the actual `RunContext` dataclass in `src/sigmalint/core/runner.py` before implementing. If filters live elsewhere on `ctx`, adjust accordingly. Either way, the FP003 rule's `getattr(ctx, "filters", None) or []` is the contract; satisfying it is a ~15-line harness change. If even that turns out blocked, **fallback**: keep FP003 contrived coverage limited to *internal-negation* shapes only, document the external-filter coverage gap in the manifest's header comment, and file a follow-up issue.

**Shape surface:** Condition AST shapes (parse → check for `has_negated_selector`), logsource categories, external filter files.

## Plan-level score-impact protocol

This plan adopts the v0.1.2-established protocol for any phase that fixes code (vs. just adds fixtures):

1. After the fix, run `sigmalint lint /tmp/sigmahq-corpus/rules --format json` with **both** the pre-fix (v0.1.2 from PyPI) and post-fix (local editable install) binaries.
2. Diff total findings + per-rule finding counts + mean-score.
3. Include the delta in the commit message and CHANGELOG under "Score impact".
